# Kristen's Excellent OS v0.1 Data Roadmap

## Current v0.1

The app is live with Supabase-backed persistence plus browser-local backup.

- Captures are saved in `public.os_state` as the current v0.1 whole-state backup.
- The browser also keeps a local fallback under `kristens-excellent-os-v0.1`.
- Each capture creates suggested review items through the mock AI classifier.
- Review item statuses persist and sync back to Supabase.
- This is still pre-auth and single-user oriented, but it is no longer just a visual prototype.

## v0.2 Memory Layer

Supabase now has a normalized capture/review layer behind the working v0.1 UI.

Tables:

- `public.os_state`: compatibility table for the current app state blob.
- `public.captures`: one row per raw capture.
- `public.extracted_items`: one row per AI-suggested item from a capture.

Automation:

- `public.sync_os_state_to_tables()` runs after `os_state` inserts/updates.
- The trigger backfills/updates `captures` and `extracted_items` from the JSON state.
- This keeps the current UI working while giving future pages real queryable records.

Views:

- `public.review_queue`: joined capture + extracted item rows for review interfaces.
- `public.dashboard_summary`: per-device counts for captures, pending review, approved items, and last activity.

Current design rule:

- `os_state` is the safety net.
- `captures` and `extracted_items` are the beginning of the real personal memory system.
- AI suggestions remain pending until Kristen approves them.

## v0.3 Approval Routing

Supabase now has first-pass destination tables for approved Review items.

Destination tables:

- `public.writing_fragments`
- `public.ideas`
- `public.calendar_events`
- `public.lsat_sessions`
- `public.contacts`

Automation:

- `public.route_approved_extracted_item()` runs after `extracted_items.status` changes.
- When a review item becomes `approved`, Supabase creates or updates the matching destination record.
- Routing is based on `suggested_destination` and `suggested_type`.
- The current UI can keep saving the v0.1 state blob while the database builds real workspace records underneath it.

Views:

- `public.destination_counts`: counts approved destination records by device and workspace.

Current routing map:

- Writing suggestions -> `writing_fragments`
- Idea suggestions -> `ideas`
- Calendar suggestions -> `calendar_events`
- LSAT suggestions -> `lsat_sessions`
- People/follow-up suggestions -> `contacts`

## Next Required Infrastructure

The next database pass should add the remaining destination tables and make the app read directly from the normalized records.

Recommended next Supabase tables:

- `media_items`
- `daily_logs`
- `devotional_entries`
- `workout_logs`
- `integrations`
- `ai_insights`
- `themes`
- `connections`

The central table remains `captures`. Everything starts as a capture, then AI creates one or more extracted items for approval.

## Google Docs End State

Google Docs should be a first-class source and destination.

Planned behavior:

- Import selected Google Docs into captures or writing memory.
- Save writing fragments and essay drafts back to Google Docs.
- Link captures, writing fragments, and drafts to source document IDs.
- Search across manually captured thoughts and selected Google Docs.
- Let AI suggest when a capture belongs in an existing document, outline, or draft.

Likely data fields:

- `google_doc_id`
- `google_doc_url`
- `google_doc_title`
- `sync_status`
- `last_synced_at`
- `source_excerpt`

## Google Calendar End State

Google Calendar should become the execution layer after review approval.

Planned behavior:

- AI suggests calendar blocks from captures.
- User approves before any event is created.
- Approved LSAT, writing, workout, follow-up, and review blocks can become Google Calendar events.
- Calendar events remain connected to the originating capture or extracted item.

Likely data fields:

- `google_calendar_event_id`
- `start_at`
- `end_at`
- `calendar_id`
- `sync_status`
- `origin_capture_id`

## OpenAI End State

The mock classifier should be replaced with an OpenAI extraction function.

Expected output for every capture:

- possible tasks
- reminders
- writing fragments
- ideas
- projects
- people/follow-ups
- devotional entries
- LSAT logs
- workout logs
- media items
- calendar events
- connections and recurring themes

The system rule stays the same: AI suggests, Kristen approves.
